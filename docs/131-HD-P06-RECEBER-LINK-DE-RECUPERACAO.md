# HD-P06 — Receber link de recuperação pelo fragmento

Recebimento compatível com template de e-mail preparado em supabase/templates/recovery.html. Link fixo do mesmo site publicado com fragmento #type=recovery&token_hash=TokenHash; não vai como query ao servidor. O template é artefato para ativação futura: não foi aplicado ao provedor, pois conector não expõe config de Auth/CLI credenciada ausente e leitura no navegador falhou duas vezes. Não sobrescrever template atual desconhecido, não alterar SMTP/CAPTCHA/redirects/grants.

Captura estrita na raiz ou index.html, sem query, fragmento inteiro limitado, exatamente type=recovery/token_hash únicos e hash limitado sem PKCE. Qualquer forma de sessão/bearer/refresh/code/param extra/duplicado é descartada. A barra é limpa imediatamente antes de init Auth. A cápsula só expõe bool/funções, segredo somente em closure; takeLink valida provider configurado e remove segredo antes de retornar uma única vez. clear abandona e impede replay. Wrapper discard anterior continua descartando, para compatibilidade.

Depois de config válida, o painel oferece o link em modo navegação, sem campo preenchido no DOM, storage ou login. Abrir/receber nunca consome o código: usuário confirma explicitamente Validar link recebido, reduzindo consumo por pré-visualização do e-mail. O destino real de verificação continua o Auth próprio, POST/token_hash/type recovery. Segredo é retirado da intenção antes do request. Cancelar antes de validar apenas apaga referência; depois segue cleanup existente e nova entrada. Nenhum workspace/discovery/me ou scope é adotado por metadata da URL. MFA/password-only permanecem como PR18/19.

## Decisões e limites

Somente fragmento hash compatível e confirmação explícita, ao custo de manter callbacks de sessão/PKCE/queries não suportados. Template do provedor não foi inspecionado/aplicado; até ativá-lo, mensagens existentes podem continuar no fluxo manual. Aplicar apenas recovery content depois de conferir branding/config atual; preservar subject, SMTP, SiteURL, allow-list, CAPTCHA, MFA e quotas. Não há promessa de entrega, aceitação real ou proteção global de todos os scanners/timing/provedores.

[Email templates Supabase](https://supabase.com/docs/guides/auth/auth-email-templates) documenta TokenHash para links próprios e ConfirmationURL padrão. O HTML preparado usa só TokenHash e destino fixo existente; o código não transforma metadados em autorização. Campos são verificados pelo próprio Auth antes do contexto privado, conforme jornada anterior. Nenhum link/OTP/senha/email real executado durante desenvolvimento.
